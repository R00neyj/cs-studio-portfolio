HOW IT WORKS

문의 하나가 답변이 되기까지

고객 문의가 들어와 답변으로 복사되기까지 다섯 단계입니다. 스크롤하면 다음 단계로 넘어갑니다.

01감지

방에 들어가지 않고 읽기

분리된 세션의 숨김 창이 방을 열지 않고 새 문의를 읽습니다. 고객 쪽에는 읽음 표시가 남지 않고 방을 여는 버튼은 두 번 눌러야 실행됩니다.

  • persist:monitor

02매칭

키워드 점수로 템플릿 찾기

템플릿 찾기에는 AI를 쓰지 않습니다. 같은 문의는 늘 같은 점수가 나오고 50점 이상인 후보만 추천합니다. 후보는 사람이 고릅니다.

03가림

보내기 전에 PC 안에서 가림

서버로 보내기 직전, 고객사·담당자·도메인은 프로젝트 사전으로, 연락처·번호는 규칙으로 자리표시로 바꿉니다. 대화에 처음 나온 이름은 가리지 못합니다.

  • call()
  • privacyTermsFor

04다듬기

서버 AI로 다듬고 검사

가린 글은 IPC, 메인, Worker를 거쳐 Claude Haiku로 갑니다. 모델은 서버가 정하고 번호·연락처·도메인이 빠진 답은 버립니다.

  • call-llm
  • /api/llm
  • keepFrom

05복사

원래 값으로 되돌리고 사람이 보내기

자리표시는 PC 안에서 원래 값으로 되돌립니다. 다듬기는 1회 실측 1.3초였고 답변은 사람이 복사해 직접 보냅니다. 앱은 메시지를 보내지 않습니다.

Engineering Decisions

운영하며 겪은 6가지 기술 문제와 해결 과정

데이터 정합성, 개인정보 보호, 읽음 표시 없는 감시, 저사양 PC 대응을 두고 내린 결정과 실제 측정값입니다.

CASE 01

보내기 전 개인정보 가림과 빠진 값 검사

사내 PC 대부분이 VRAM 4GB 환경이라 대화 요약과 초안 다듬기에 서버 AI를 써야 했지만 고객사 이름·도메인·연락처가 외부로 나가는 문제가 있었습니다. 개체명 인식(NER) 모델을 쓰면 그 자체가 서버 호출이 되므로, 프로젝트 이름 사전(privacyTermsFor)과 정규식 규칙으로 보내기 직전 [고객사1], [도메인1], [연락처1], [번호1]로 바꾸고 답을 받은 뒤 되돌렸습니다.

한계와 빠진 값 검사: 사전과 규칙만 쓰므로 대화에 처음 나온 이름은 가리지 못합니다. 다듬은 답에서 초안의 번호(10자리 이상 계좌 등)·연락처·이메일·도메인 자리표시가 빠지면(keepFrom) 그 답을 버리고 원래 초안을 씁니다.

CASE 02

읽음 표시를 남기지 않는 채널 감시와 후속 메시지 합치기

데스크톱 앱이 새 문의를 확인하려고 채팅방을 직접 눌러 열면 '읽음' 표시가 남아 정작 담당자가 문의를 놓치는 문제가 있었습니다. 별도 파티션의 숨김 BrowserWindow에서 방을 열지 않는 내부 대화 조회 API만 호출해 안 읽음 상태를 유지하고 실제 채팅방 열기는 두 번 누르기(useArmedAction)로 막았습니다.

후속 메시지 합치기: 견적을 내는 동안 같은 방에 새 메시지가 오면 다른 문의로 쪼개지지 않게 보고 복사 시각(reportCopiedAt)을 기준으로 진행 중인 건에 합쳤습니다.

CASE 03

로컬 OCR 엔진 선정(96%)과 빨간 표시 찾기 실험

실제 고객 수정 요청 사진 16장(정답 문구 169개)을 채점해 Windows OCR(72%), EasyOCR(66%), Tesseract(47%) 가운데 가장 정확했던 PaddleOCR(96%, 163/169)을 골랐습니다. 화면 전체 글자를 AI에 넘기면 배너 광고 문구까지 세어 합성 15장(정답 45건)에서 66건으로 부풀리는 문제를 줄이려고 지시 줄 분리(51건)와 빨간 표시 찾기(합성 15장 45/45건)를 시험했습니다.

한계와 판단 근거: 빨간 표시 찾기는 합성 15장과 실제 사진 표본에서는 모두 맞았으나, 사이트에 원래 있는 빨간 테두리 버튼·오류 입력칸과 고객이 그린 네모를 구분할 수 없어 기본 적용 대신 실험실(선택 켜기) 기능으로 두었습니다.

CASE 04

노션 동기화 응답 45% 절감과 D1 행 단위 상태 기록

500여 개 프로젝트를 Worker Cron으로 가져올 때 전체 칸 응답이 3.8MB(4.3초)에 달하고 FTP·호스팅 계정 정보 칸까지 넘어올 위험이 있었습니다. filter_properties로 필요한 칸만 받아 2.1MB(2.5초)로 45% 줄였고 관계형 담당자 DB 연결이 빠지면 빈 배열로 덮어쓰지 않도록 막았습니다.

CPU 한계 관리와 동시 수정 보호: JSON 파싱에만 약 6~7ms가 걸려 무료 플랜 Worker CPU 한도(10ms)에 가까워질 수 있습니다. 그래서 notion_sync에 결과를 남기고, 한도에 걸리면 last_edited_time으로 바뀐 행만 받는 방식으로 줄이기로 했습니다. 프로젝트 수정은 바뀐 것만 보내는 /api/projects/changes로, 만료 안내 기록은 D1 행 단위 + expect(현재 단계 일치 조건)로 나눴습니다.

CASE 05

앱 내장 토큰 없는 비공개 릴리스 302 자동 업데이트

비공개 GitHub 저장소에서 electron-updater 기본 GitHub 방식을 쓰면 앱 파일 안에 GH_TOKEN을 넣어야 하는 보안 문제가 있었습니다. 대신 Generic 방식을 쓰고 Worker /api/update/<파일>가 앱의 HMAC 세션 토큰을 확인한 뒤 GitHub 임시 서명 주소로 302 응답을 보내 넘기도록 만들었습니다.

토큰 보호와 수동 재시작: 다른 호스트로 넘어갈 때 Authorization 헤더가 자동으로 지워져 세션 토큰이 외부로 새지 않습니다. 상담 중 앱이 갑자기 닫히지 않도록 백그라운드로 받은 뒤 사람이 '재시작해서 업데이트'를 눌렀을 때만 설치합니다.

CASE 06

외부 호스팅 사이트의 세션 아이디 꼬임 원인과 복구

호스팅 만료 목록을 처음 불러올 때는 자사 도메인 201개가 정상으로 나오지만 같은 앱 실행에서 다시 불러오면 모든 도메인이 '확인 필요(0개)'로 바뀌는 버그가 있었습니다. 호스팅별 부가 설정을 읽는 하위 요청이 서버 세션의 선택 아이디를 개별 호스팅 아이디로 바꾼 채 남겨 두고 있었습니다.

해결 결과: 상단 메뉴 DOM에서 대표 회원 아이디를 읽어 조회 직후 세션을 원래 아이디로 되돌렸습니다. 같은 세션에서 다시 불러와도 자사 도메인 판정이 그대로인 것을 확인했습니다.
